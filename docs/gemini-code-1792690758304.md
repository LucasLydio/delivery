# Real-Time Architecture for Delivery Apps on Freemium Netlify & Supabase

In a delivery context (e.g., tracking an order from "Pending" to "Preparing" to "Out for Delivery"), users expect real-time updates. However, implementing real-time tracking poorly will instantly exhaust Netlify's Free Tier limits (125,000 requests/month and 100 compute hours). 

Here is how to navigate Polling, Server-Sent Events (SSE), and WebSockets under these constraints.

---

## 1. The Approaches: What Works and What Fails

### ❌ Polling (The Quota Killer)
Polling means the frontend requests the order status every `X` seconds. 
* **How it interacts with Netlify:** Every single poll counts as 1 request against your 125,000 limit. 
* **The Math:** If a user waits 30 minutes for a pizza and your app polls every 10 seconds, that one user consumes **180 requests**. You would hit your Netlify limit with just ~700 daily orders.
* **Verdict:** Do not use continuous polling on Netlify.

### ⚠️ Server-Sent Events (SSE) via Netlify (The Compute Drain)
SSE keeps a single HTTP connection open so the server can stream updates to the client.
* **How it interacts with Netlify:** Standard Netlify Serverless Functions have a maximum execution timeout (default 10s, max 26s for sync functions). You cannot keep a standard function open indefinitely for SSE. Even if you use Netlify Edge Functions (which support streaming), keeping the connection open drains your **Compute Credits (GB-hours)** rapidly.
* **Verdict:** Avoid using Netlify compute to hold open SSE connections.

### ✅ WebSockets via Supabase Realtime (The Freemium Savior)
WebSockets maintain a persistent, two-way connection.
* **How it interacts with Netlify:** **It doesn't.** By connecting your frontend directly to Supabase via `supabase.channel()`, you bypass Netlify completely. 
* **The Math:** Netlify sees **0 requests**. Supabase Free Tier allows **5,000 concurrent active connections** and **2 million messages** per month.
* **Verdict:** This is the strictly correct architecture for a delivery app on this stack.

## 2. Best Practices for Delivery Apps

If you are building a delivery tracker, implement these specific strategies:

### Offload Real-Time Exclusively to Supabase
Instead of hitting a Netlify API route to check order status, subscribe to database changes directly from the client browser:
```javascript
// Frontend Code: Listen to changes on the user's specific order
const orderId = '12345';
const channel = supabase
  .channel(`order_tracking_${orderId}`)
  .on(
    'postgres_changes',
    { event: 'UPDATE', schema: 'public', table: 'orders', filter: `id=eq.${orderId}` },
    (payload) => {
      console.log('Order status changed to:', payload.new.status);
      // Update UI: "Your food is being prepared!"
    }
  )
  .subscribe();
  
```

### Implement "Smart" / Adaptive Polling (If WebSockets Fail)

If corporate firewalls block WebSockets and you must fallback to polling Netlify, make the polling interval dynamic based on the delivery state:

Pending (Restaurant hasn't accepted yet): Poll every 30 seconds.

Preparing (Food is cooking): Poll every 3 to 5 minutes (status won't change quickly).

Out for Delivery: Poll every 15 seconds.

Delivered: Stop polling immediately. (Crucial: failing to unmount the polling interval is the #1 cause of background quota drain).

Use Web Push Notifications
Instead of requiring the user to stare at an active screen (holding a WebSocket open or polling), use the browser's native Web Push API or Firebase Cloud Messaging (FCM).

The user closes the app.

Your backend database triggers a webhook only when the status changes.

The user gets a push notification ("Your driver is arriving!").

Cost: 0 persistent connections, 0 Netlify polling requests.

## 3. Developer Checklist to Prevent Limit Abuse
Before deploying your delivery tracking UI to production, verify the following:

[ ] No setInterval API calls: Ensure there are no recurring intervals hitting /api/orders/:id on the frontend.

[ ] Cleanup Subscriptions: Ensure supabase.removeChannel(channel) or clearInterval() is called in the ngOnDestroy (Angular) or useEffect cleanup (React) when the user navigates away from the tracking page.

[ ] Background Tab Throttling: If using WebSockets, ensure you pause or disconnect the channel if the user minimizes the app or switches tabs (using the Page Visibility API).

[ ] No Auto-Refresh on Errors: If an API request fails, do not write a loop that aggressively retries immediately. Implement exponential backoff (retry after 2s, then 4s, then 8s) to prevent a localized outage from causing a massive spike in Netlify requests.
